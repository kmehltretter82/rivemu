# Review of rivemu and rivemu-lockstep, 2026-11-02

This review covers `rivemu` (base `0946319`) and `rivemu-lockstep` (base
`197993f`), the follow-up work on branch `claude/trusting-bell-xvhb0r` in
both repositories, and the validation claims in
[`VALIDATION_STATUS.md`](VALIDATION_STATUS.md). It focuses on three areas:

- privileged, MMU and trap semantics;
- what the lockstep comparison leaves out, and why;
- the Sail and QEMU GDB transport.

Every finding cites at least one of these:

- a test that fails without the fix;
- a command and its output (logs under `docs/evidence/`);
- a specification citation.

All runs were on a Claude Code cloud container (Linux 6.18, x86_64, 4 vCPUs).

### Details for open and newly fixed findings

**10. `mcycle` vs `minstret`.** The privileged spec defines them as two
counters with separate inhibit bits (`mcountinhibit.CY` = bit 0, `.IR` =
bit 2). Smcntrpmf filters them by `mcyclecfg` and `minstretcfg`. rivemu
returned `minstret` for `mcycle`/`cycle` and wrote both through one
field. ACT `Sm_mcsr_cntr-00` sets CY, writes `mcycle`, and expects to
read back the written value; rivemu returned 7 instead of 0. The fix
adds a separate `mcycle`. It still counts one cycle per retired
instruction, but it is now inhibited, filtered and written independently.
The snapshot format gains the field: magic `RIVSNAP3`; `RIVSNAP2` still
loads, with `mcycle = minstret`. The new test fails on the old code
(`left: Some(5), right: Some(0)`) and passes after the fix.

**11. CBO PMA checks.** Sail 0.16 `process_clean_inval` calls
`phys_access_check`, which requires a PMA region that is readable or
writable for `CB_manage` (`sys/mem.sail:145`), and raises a store/AMO
access fault otherwise. ACT test case 10 ("Leaf PTE points to the
access-fault region") maps a page to `RVMODEL_ACCESS_FAULT_ADDRESS`
(0x100, unmapped on `virt`) and expects that fault. rivemu raised
nothing, so every later trap in the test was compared against the wrong
expected trap. QEMU has the same bug (QEMU issue 3501; riscv-arch-test
excludes these tests for QEMU). The fix adds the PMA check after PMP:

- `cbo.clean`/`flush`/`inval` need a mapped region;
- `cbo.zero` needs RAM, as in Sail, where MMIO has
  `supports_cbo_zero = false`.

**12. `mstateen` reset.** Sail implements the quoted sentence in
`sys_control.sail:592` (`reset_stateen()`), and QEMU 11.1.3 resets the
registers to 0. rivemu reset them to `M0_MASK` (SE, ENVCFG, CONTEXT,
SRMCFG), so OpenSBI v1.7 read `0xc280000000000000` where QEMU read 0.
`Hart::init_smode_boot`, which stands in for firmware, now enables them,
as OpenSBI's `mstatus_init` does. Linux under the built-in SBI is
unaffected.

**15. RVA23 claim.** The RVA23 profile lists H as mandatory in RVA23S64,
and Zama16b as mandatory in RVA23U64. With Zama16b, misaligned AMOs that
stay inside a naturally aligned 16-byte granule execute; rivemu raises
address-misaligned for all of them. Either implement Zama16b (and H) or
change the README to "RVA23U64 subset without Zama16b; no H".

**16. PMP with no matching entry.** OpenSBI always programs PMP, so Linux
does not hit this. Bare-metal programs that drop to S/U mode without
programming PMP run on rivemu but fault on Sail and on QEMU with PMP
enabled. `-strict` gives spec behavior. Making strict the default would
need the built-in SBI path to program PMP (it already does in
`init_smode_boot`).

## 2. What the lockstep comparison leaves out, and why

`ArchState::diff` (`rivemu-lockstep/src/lib.rs`) compares:

- always: `pc`, `x1..x31`, `f0..f31`, `fcsr[7:0]`;
- with `--check-csrs` (and in privileged suites): the privilege mode,
  `mstatus` under `MSTATUS_COMPARE_MASK = 0x0000_0600_01fe_19aa`, `mepc`,
  `mcause`, `sepc`, `scause`, `stvec`, `medeleg`, `satp`;
- in RISU suites: the 4 KiB scratch memory region, after each block (or
  after each instruction with `--step-check`).

Not compared, with the reason:

| Left out | Why | Consequence / mitigation |
|---|---|---|
| `mtval`, `stval` for illegal-instruction and other non-address exceptions | Both 0 and the faulting instruction are legal for illegal instruction. | Covered by ACT's trap signatures instead. For misaligned, access and page faults (causes 0/1/4/5/6/7/12/13/15), where Sstvala fixes the value, lockstep now compares `xtval` whenever both sides report the same cause (rivemu-lockstep, `ArchState::diff`). 36/36 suites and the fault-heavy suites at 128 blocks pass with it. |
| `mstatus` FS, VS, XS, SD, UXL/SXL | FS/VS dirty tracking is implementation-defined in precision (QEMU sets Dirty eagerly). | A missing dirty update is not caught. ACT `Sm_mstatus_sd` covers SD. |
| `mie`, `mip`, `mideleg`, `mtvec`, `mscratch`, `sscratch`, `mcounteren`, `scounteren`, `menvcfg`, `senvcfg`, `mstateen*`, `stimecmp`, `pmp*` | Not in `ArchState`. Interrupt state depends on timing; the rest only shows up when software reads it. | A difference surfaces only when a later instruction reads the CSR. That is how findings 8 and 12 and the harness mismatches below were found. |
| `cycle`, `time`, `instret`, hpmcounters | Timing-dependent. | Not compared. |
| `v0..v31`, `vl`, `vtype`, `vstart` | Not in `ArchState`. | `Suite::Vector`'s epilogue stores all 32 vector registers to scratch memory and copies `vl`/`vtype`/`vstart` into GPRs (`3c57b83`). |
| Memory outside the scratch region | Too large to compare per step. | Boot lockstep compares registers only; a memory difference surfaces when it is loaded. |
| QEMU in ordinary suites without `--step-check` | Block checkpoints only. | A transient difference overwritten before the checkpoint is missed. All campaign evidence below uses `--step-check`. |

Boot lockstep (`rivemu-lockstep boot`) starts QEMU from rivemu's reset
state through `set_state`, which only covers `ArchState`. Every CSR whose

## 3. Sail and QEMU GDB transport

**Cause of "Connection reset by peer" (finding 1).** `pick_free_port()`
bound a probe `TcpListener` on `127.0.0.1:0`, dropped it, and the caller
polled `connect()` until Sail accepted. A concurrent `Command::spawn` in
another worker thread copies the fd table into the child, and the
dropped probe stays open there until that child calls `execve`. A
`connect()` in that window completes in the probe's backlog, and is
reset when the child execs. Separately, two workers could be given the
same port. The second Sail then failed to bind, and both clients
connected to the first Sail, which accepts only one client.

Evidence is in `rivemu-lockstep/docs/evidence/2026-11-02-sail-startup/`:

- a 60-line standalone reproduction (`forkleak.rs`): 0 of 20,000
  connections reached a dropped probe without concurrent spawns, and 145
  did with them (142 reset);
- instrumented failing campaign runs.

**Fix (`f57eb73`), without serializing startups.**

- Sail ports are reserved in-process from 20000–29999, below the Linux
  and macOS ephemeral ranges, and no probe is ever bound.
- The client connects only after Sail prints `Listening on port N`, and
  retries on another port if Sail reports `Address already in use`.
- QEMU serves its GDB stub on a per-process, per-spawn Unix socket.

**Result.** `campaign --reference sail --suite alu --workers 6 --blocks
300 --insns 16`:

| Transport | Clean runs | Time per run |
|---|---|---|
| New, lock-free | 25 of 25 | 5.7–6.4 s |
| Old, lock-free | 17 of 24 | 6.6–6.9 s |
| Startup lock | 8 of 8 | 9.7–10.5 s |

`tests/spawn_stress.rs`, with 240 QEMU and 240 Sail startups from 6
threads, failed 2 of 5 runs before the fix and passed 10 of 10 after
(4,800 startups).

**QEMU latency (`301f46e`).** Boot lockstep ran at about 260
instructions/s because every step made 46 sequential GDB round trips and
read each reply one byte per `read()`. `examples/qemu_latency.rs` shows
QEMU's gdbstub is the limit: a step takes 192 µs, and one `p` packet
16–25 µs. Buffered reads, pipelining and boot-mode partial reads give
16× (5,000 steps: 19.23 s → 1.20 s), and a full re-read every 1,000 steps
and on any difference keeps the cache from hiding a divergence.

## 4. riscv-arch-test privileged subset

Before this review, `VALIDATION_STATUS.md` listed the privileged subset as
"Not verified". It is now run with riscv-arch-test `2dc36dd`, Sail 0.16 as
the reference, and the DUT configuration in
[`tests/arch-test/rivemu-rv64/`](../tests/arch-test/README.md). The run
covers 418 self-checking tests from the 15 privileged suites:

- `InterruptsS`, `InterruptsSm`, `PMP`, `S`, `Sm`, `Sstc`;
- `Sv` (Sv39/48/57 with exceptions, Zaamo, Zalrsc, Zicbo);
- `Svade`, `Svadu`, `Svbare`, `Svinval`, `Svnapot`, `Svpbmt`, `Svvptc`;
- `U`.

`SsstrictV` is excluded because Sail 0.16 does not model it.

| rivemu | Passed | Failed | Log |
|---|---|---|---|
| `29434f1` | 411 | 7 | `docs/evidence/2026-11-02/arch-test/summary-before-29434f1.txt`, `failures-before-29434f1/` |
| `9b91323` | **418** | **0** | `docs/evidence/2026-11-02/arch-test/summary-after.txt` |

The failures were three rivemu bugs, now fixed:

- **`mcycle` aliased to `minstret` (finding 10).** Shown by
  `Sm_mcsr_cntr-00` `cp_inhibit_mcycle`: bad value 7, expected 0.
- **The `time` CSR did not follow a guest write to `mtime` (finding 13).**
  Shown by `Sm_mcsr_cntr-00` `cp_mtime_write` once the first fix was in.
  The CLINT kept the write as a private offset, while the harts and Sstc
  read the shared timebase. The privileged spec defines `time` as a
  read-only shadow of `mtime`. The fix moves the shared timebase on a
  guest write. New test: `clint::tests::mtime_write_moves_the_shared_timebase`.
- **CBOs skipped the PMA check (finding 11).** Shown by six
  `Sv_Zicbo_*_zicbom_exceptions` tests.

The configuration is derived from riscv-arch-test's QEMU "max" config.
The first run still had QEMU's settings for VLEN (128), `misa.B`,
`marchid` (5), Svukte (off) and misaligned AMOs, and failed 21 tests: 14
from those settings and the 7 above. Two of the settings record rivemu
implementation choices the spec allows: `misa.B` = 0 (finding 19), and
address-misaligned rather than access fault for misaligned AMOs (but see
finding 15 on Zama16b).

Sail 0.16 treats Svukte as experimental: `hartSupports(Ext_Svukte)`
requires `--enable-experimental-extensions`. The ELFs are therefore built
with `ENABLE_EXPERIMENTAL_EXTENSIONS=True`. Without it, Sail expects
`senvcfg.UKTE` to be read-only zero, and 3 tests fail on bit 8.

Not covered:

- the unprivileged `rv64i` suites (about 1,000 tests; riscv-tests and the
  lockstep campaigns cover them partly);
- H;
- Smstateen/Ssstateen, Sscofpmf, Zicfilp/Zicfiss, Ssnpm and Sdtrig, which
  have no tests in this riscv-arch-test revision's privileged tree.

## 7. Boot time (P17)

P17 targets less than 8 s (SMP1) and 10 s (SMP4) to a shell. The earlier
isolated campaign on an M-series host measured medians of 18.9 s and 21.1 s
with the Debian kernel.

**Profile.** Callgrind on an SMP1 boot (OpenSBI v1.7 + Linux 6.12) during
OpenSBI and early kernel boot, 155 G host instructions (`Ir`):

| Function (self) | Share |
|---|---|
| `Hart::pmp_check` and inlined helpers | **19.2%** (177 M calls from `translate_with_ram_off`) |
| `Hart::execute` | 15.5% |
| `Hart::run` | 10.7% |
| `translate_with_ram_off` | 10.7% |
| `populate_bbcache_same_page` | 6.9% self, 24.4% inclusive (39 M calls) |
| `decode` + `decode_compressed` | 11.0% |

**Cause of the PMP cost.** OpenSBI programs eight PMP regions with a
catch-all as the last entry, and with Smepmp sets `mseccfg.MML`. That keeps
`pmp_enforced` on. Every S/U TLB hit therefore ran a linear `pmp_check` over
the entries and gave up the fast RAM path (`ram_off = u64::MAX`). The
built-in SBI avoids this because its entry 0 is an open NAPOT catch-all.

**Fix (`02d1f3c`).** A 256-entry direct-mapped cache of PMP verdicts per physical page,
per access type, and per privilege class (M vs S/U). It is used only while
every PMP entry starts and ends on a 4 KiB boundary (`!pmp_subpage`), so
the same entries match every byte of a page. `update_pmp_state`
invalidates it through an epoch counter, so it is never stale; the spec
would also allow requiring an `SFENCE.VMA`. TLB hits keep the fast RAM
path whenever `!pmp_subpage`. Test:
`pmp_page_cache_follows_pmp_writes_and_privilege`.

**Result.** Same machine, interleaved runs, 5 each, boot to
`RIVEMU_SMOKE_OK` and poweroff (`docs/evidence/2026-11-02/boot-bench-pmp-cache.txt`):

|---|---|---|
| base `0946319` | 11.16 s (10.89–11.61) | 15.30 s (14.21–16.39) |
| head `b0af485` | 10.87 s (10.74–12.01) | 16.77 s (14.47–17.63) |
| head + PMP page cache | **9.46 s** (8.42–10.76) | **13.00 s** (11.89–14.31) |

That is 13% (SMP1) and 22% (SMP4) faster than head. Base vs head is within

**Second round (`207c7dc`): measured, not guessed.** The first profile
covered only early boot, and it ran without `-icount`. The guest timer
